## 프로젝트 세부 내용

### 개발 배경 및 목적

LLM 서비스 운영비의 대부분은 추론 비용이고, 실제 트래픽의 상당수는 저렴한 모델로도
충분한 단순 질의다. 그럼에도 많은 서비스가 모든 요청을 고성능 모델로 보내 예산을
낭비한다. 이 프로젝트는 "쉬운 질문은 싸게, 어려운 질문만 비싸게"를 자동으로 판단하는
라우터를 오픈소스로 구현해, 같은 예산에서 더 높은 평균 품질을 얻는 것을 목표로 한다.

과제의 제약은 실제 서비스 환경을 반영한다. 라우터는 모델을 호출할 수 없고, 답변을
비교하거나 선택을 번복할 수도 없다. 프롬프트 내용과 예산 등급만 보고 한 번에 정해야
하며, 예산을 넘기면 해당 등급은 0점이다. 운영에서 대기열 폭증이나 응답 지연으로
이어지는 상황을 그대로 옮긴 조건이다.

### 개발환경

- 언어·런타임: Python 3.11, 컨테이너 `linux/arm64` (Debian slim)
- 학습: scikit-learn 1.8, SciPy 1.17, NumPy 1.26 (로컬 CPU)
- **실행 의존성: NumPy 하나** — 학습용 패키지는 제출 이미지에 넣지 않는다
- 실행 조건(공식): CPU 2코어, 메모리 2GiB, 네트워크 없음, 읽기 전용 루트,
  등급당 90초
- 개발 도구: Git, Docker Buildx, 표준 라이브러리 unittest

```

          ├─ TF-IDF 단어 1–2그램 (6만)

            · 예측 입력 토큰 1
                    │
                    ▼
          배치 선택 정책
            · 예측 이득 ÷ 예측 비용이 큰 순서로 승격
            · 동률은 프롬프트 내용 해시로만 정렬 (문항 ID·순서 미사용)
            · 등급별 예산 마진과 추론 모델 선택 건수 상한 적용
                    │
                    ▼
          등급별 선택 결과 JSON (문항당 model_id 하나)
```

### 프로젝트 상세 내용

**(1) 비용을 예측 대상에 포함했다.** 라우팅 시점에는 토큰 수가 주어지지 않는다.
그래서 품질뿐 아니라 모델별 출력 토큰과 입력 토큰까지 회귀로 예측하고, 공개 비용
정책으로 비용을 환산한다. 학습에서도 실제 토큰 수 대신 예측값으로 비용을 계산해
추론과 조건을 일치시켰다. 로그 공간 회귀를 지수로 되돌리면 평균이 과소평가되므로
(Jensen 부등식), 잔차 분위수만큼 상향한 뒤 학습 분할의 실제 총비용에 맞도록 모델별
스케일을 보정한다.

**(2) 예산 초과를 구조적으로 차단했다.** 추론 모델(`axk1-think`)은 출력 토큰 분포의
꼬리가 매우 두껍다. 공개 자료에서 중앙값이 1,570토큰인데 최대는 130,504토큰으로,
단 한 문항이 경량 모델 전체 비용의 26%를 소모할 수 있다. 몇 건만 빗나가도 등급이
통째로 0점이 된다.

세 가지 방어책을 실험했다. 문항별 예측 비용에 상한을 두는 방식과 분위수 회귀로 위험을
추정하는 방식은 모두 실패했다. 사고를 일으키는 문항은 "예측은 작은데 실제가 큰"
것들이라 예측값에 의존하는 필터를 그대로 통과하기 때문이다. 효과가 있었던 것은 추론
모델의 **선택 건수 자체를 상한으로 묶는 것**이었다. 예측 오차와 무관하게 노출이 물리적으로
제한되며, 고비용 구간은 승격 이득 대비 비용도 가장 나쁜 구간이라 점수 손실도 작다.

**(3) 순서에 의존하지 않는 배치 정책.** 예산은 배치 전체에 걸린 제약이므로 문항을
독립적으로 처리할 수 없다. 그렇다고 입력 순서에 의존하면 규칙 위반이다. 그래서 승격
후보를 이득/비용비로 정렬하되, 동률은 **프롬프트 내용의 SHA-256 해시**로만 깬다.
문항 ID·입력 순서·출처를 어느 단계에서도 읽지 않으므로, 운영자가 순서를 섞고 ID를
바꿔 재실행해도 같은 결과가 나온다.

**(4) 학습과 실행의 분리.** 학습은 scikit-learn으로 하되 제출 이미지에는 NumPy만
넣는다. scikit-learn `TfidfVectorizer`의 동작(소문자화, 토큰 패턴, `char_wb` 패딩,
sublinear tf, smooth idf, 블록별 L2 정규화)을 표준 라이브러리로 재현했고, 두 경로의
예측 차이는 1.2e-15로 부동소수점 한계까지 일치한다. 개발 중 이 재현이 어긋나
(블록별이 아닌 전체 정규화) 세 등급 모두 예산을 넘기는 결함이 있었는데, 자체 점검
도구로 잡아 수정했다.

**(5) 등급별 설정은 교차검증으로 정했다.** 2,640문항을 5-fold와 8-fold로 나눠
등급별 (추론모델 상한, 예산 마진) 조합을 탐색했고, 양쪽 fold 구성에서 예산 초과가
0건인 설정만 후보로 삼았다.

| 등급 | 추론모델 상한 | 예산 마진 | 공개 Dev 예산 사용률 |
|---|---:|---:|---:|
| fast | 0% | 0.85 | 한도의 82.9% |
| balanced | 1% | 0.80 | 한도의 80.1% |
| premium | 11% | 0.85 | 한도의 64.7% |

여기에 추론 모델 승격 1건이 쓸 수 있는 비용에도 상한(경량 총비용의 5%)을 둔다.
건수만 묶으면 비싼 문항 몇 건이 예산을 독차지할 수 있기 때문이다.

### 구동 및 시연

**성능**

변동이 크기 때문이며, 안전 판단은 이 수치를 기준으로 했다.

### 향후 확장성 및 기대효과

라우터는 특정 모델군에 묶여 있지 않다. 후보 모델의 품질·토큰 사용량 기록과 비용
정책만 있으면 어떤 조합에도 재학습할 수 있고, 학습 스크립트와 평가 도구를 함께
공개하므로 사내 모델 구성에 맞춘 재현이 가능하다. 네트워크와 GPU 없이 CPU 2코어에서
동작하므로 사내망·온프레미스·공공 환경에 그대로 넣을 수 있고, 아티팩트가 5.5MB라
엣지 환경에도 실린다. 대규모 트래픽을 다루는 고객센터·검색·공공 AI 서비스에서 같은
예산으로 더 나은 품질을, 또는 같은 품질을 더 낮은 비용으로 제공하는 데 쓸 수 있다.

### 프로젝트의 혁신성 및 차별성

1. **예산 초과를 예측 정확도가 아니라 구조로 막는다.** 예측 기반 방어책이 실패하는
   이유(예측이 작은 문항이 실제로 클 때 걸러지지 않음)를 실험으로 규명하고, 선택
   건수 상한이라는 예측 무관 장치로 대체했다.
2. **순서 불변성을 설계 단계에서 보장한다.** 배치 최적화를 하면서도 동률 정렬 키를
   프롬프트 내용 해시로 두어, 감사 항목을 사후 확인이 아니라 구조로 만족한다.
3. **학습·실행 경로 일치를 수치로 증명한다.** 두 경로의 예측 차이 1.2e-15를 시험으로
   고정해, 라이브러리 없는 실행 환경에서도 학습 결과가 그대로 재현됨을 보장한다.
4. **제출 전 자체 점검 도구를 함께 제공한다.** 규칙 준수·결정성·엣지 케이스·시간·예산을
   한 명령으로 확인하고, 예산이 한도의 97%를 넘으면 경고한다.
5. **도달 가능 상한을 분석해 개발 방향을 정했다.** 정보 수준별로 도달 점수를 계산해
   (전부 경량 0.605 / 비용만 정확 0.683 / K1 이득 완전정보 0.725 / 완전정보 0.792)
   남은 개선 여지가 어디에 있는지 정량화했다. 품질 차이의 상당 부분은 생성 2~4회
   평균의 흔들림이라 원리적으로 예측할 수 없다는 것도 함께 보였다.
6. **측정에 근거해 두 번 되돌렸다.** 부스팅 트리는 토큰 예측 상관을 0.37에서 0.65로
   올렸고 단일 측정 점수도 가장 높았지만, 교차검증에서 어떤 마진으로도 예산을 지키지
   못해 채택하지 않았다. 문장 임베딩은 오히려 예측을 떨어뜨렸다(상관 0.425 → 0.372).
   좋아 보이는 수치가 아니라 안전이 검증된 구성을 택했다.

### 한계점 및 향후 발전 로드맵

- **품질 예측의 한계**: 경량 모델과 중형 모델의 품질 차이는 예측 상관이 0.01~0.10으로
  사실상 예측되지 않는다. 점수가 생성 2~4회의 평균이라 노이즈가 지배적이기 때문이다.
  부스팅 트리와 다국어 문장 임베딩을 모두 시험했으나 이 한계는 넘지 못했다.
  반복 횟수가 늘어난 자료가 생기면 개선될 여지가 있다.
- **예산 여유의 비용**: 안전을 위해 예산의 17~30%를 남긴다. 비용 예측 정확도를 높이면
  같은 안전 수준에서 더 쓸 수 있다. 출력 토큰 예측 상관을 올리는 것이 다음 과제다.
- **이미지 크기**: 73MB다. 선형 연산을 순수 파이썬으로 옮겨 NumPy를 빼면 더 줄일 수
  있으나, 현재 실행 시간이 한도의 5%라 급하지 않다.
- **로드맵**: (1) 출력 길이 예측 강화로 예산 활용률 개선, (2) 문서 임베딩을 더한
  품질 예측 개선, (3) 실시간 서빙용 온라인 예산 컨트롤러, (4) 다른 모델군·비용
  정책으로의 이식 사례 추가.

### 소감 및 후기

가장 많은 시간을 쓴 것은 점수를 올리는 일이 아니라 **0점을 피하는 일**이었다. 예산을
한도까지 채우는 정책은 공개 자료에서 잘 작동하다가 분할을 바꾸면 초과했고, 그때마다
등급 점수가 통째로 사라졌다. 평균을 조절하는 마진으로는 두꺼운 꼬리를 막지 못한다는
것을 여러 실패 끝에 확인하고 나서야, 위험을 예측하려 들지 말고 노출 자체를 묶는
방향으로 바꿀 수 있었다.

학습 코드와 실행 코드가 갈라진 지점에서 예측이 어긋난 결함도 뼈아팠다. 공식 검증은
통과했지만 실제로는 세 등급 모두 예산을 넘기는 상태였고, 자체 점검 도구를 만들지
않았다면 제출 후에야 알았을 것이다. 검증을 코드로 만들어 두는 일이 왜 기능 개발만큼
중요한지 체감했다.
